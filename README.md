# MARFAGENEZ

**Исследование минимальных условий, при которых система поддерживает собственную организацию в среде, из которой она берёт вещество и энергию.**

Marfagenez — исследовательский стенд, а не продукт и не образовательная система.
Он состоит из исполняемой модели на Rust, формальных доказательств на Lean 4 и
Verus, независимых численных проверок на Python и JavaScript и корпуса
документов, где каждое утверждение имеет уровень доказанности и команду
воспроизведения.

Проект развивается от первых принципов: заранее не задаётся ни конечная форма
организма, ни желательное поведение. Реализуются базовые механизмы —
ресурс, затраты, урон, починка, движение, память, дележ — и измеряется, какие
структуры динамика допускает, а какие приходится навязывать правилами.

## Исследовательский вопрос

Что делает систему живой, а не просто долго существующей?

Рабочая формулировка: **слон** — система, которая поддерживает себя как часть
среды, из которой берёт вещество и энергию. У слона выделены части, и каждая
исследуется отдельно (`GOAL.md` §1a):

| часть | что это | состояние |
|---|---|---|
| **желудок** | превращение взятого в поддержание | закон доказан |
| **ноги** | перемещение и его цена | закон доказан |
| **память** | что система знает о среде | измерено частично |
| **стадо** | что происходит при многих | закон доказан частично |
| **хобот** | как система достаёт вещество | **не сделано**: чтение — одно число, без цены и без выбора |
| **кожа** | где граница и что её держит | **не сделано**: границы как состояния нет; `structure` удалён 2026-11-14 как тень урона (см. ниже) |

Критерием успеха **не** считаются рост сложности, продолжительность жизни,
численность и разнообразие сами по себе. Это наблюдаемые величины, а не цели.
Что именно не считается результатом — `GOAL.md` §2 и `NOT-CLAIMED.md`.

### Законы движения (уровень A)

| закон | формула |
|---|---|
| насыщение | `spread = min(σ√t, B/√3)` |
| гонка | комната заполняется за 1 шаг при `(B/σ)²` организмах |
| время до стены | `t* < B/μ` |
| наклон (предел) | `α = 2μ/σ²` |

Отдельный отрицательный результат: **шар не сохраняет меру** при складывании
(`χ² = 3·10⁷`). Это записано как находка, а не как ошибка: наивное ожидание
«складывание сохраняет равномерность» ложно.

### Поведение и среда (уровень C)

- **Порядок взгляда решает, работает ли память**: `LookThenEat` и `EatThenLook`
  дают разные исходы (`docs/FINDING-142-the-look-order-decides-whether-memory-works.md`).
- **Слепая память никогда не отдыхает**: политика `Remember` — одноразовый
  выбор, а не память (`docs/FINDING-remember-is-choice.md`).
- **Скученность — это число кормящихся клеток**, а не число организмов.
- **Богатая клетка кормит одного**; чередующееся поле схлопывается.

### Поддержание себя (уровень B)

```
sustains  ⟺  (income − maintenance_cost) ≥ damage_rate · repair_cost
is_viable ⟺  income > maintenance_cost          (необходимо, не достаточно)
death     ⟺  energy ≤ 0  ∨  damage ≥ 1
```

**Главный вывод о слоне.** Поддержание себя в текущей модели — **арифметика, а
не процесс**. `World::sustains()` (`core/src/organism.rs:297-301`) — предикат от
четырёх чисел. Состояния «способность чинить» не существует, поэтому ремонт
второго порядка (урон, разрушающий способность чинить) невозможен по
построению. Это не находка о слоне, это находка о том, где слона нет.

**Умолчания стоят вне окна.** `World::default()` (`core/src/organism.rs:232-246`):
`income 1.0`, `maintenance_cost 0.6`, `repair_cost 1.5`, `damage_rate 0.01`.
Отношение цены поддержания к доходу

```
ρ = damage_rate · repair_cost / income = 0.01 · 1.5 / 1.0 = 0.015
ρ_s = damage_rate · repair_cost / (income − maintenance)
```

то есть починка стоит 1.5% дохода. **Прогоны на умолчаниях не измеряют
поддержание себя.** Они измеряют движение, память и дележ в мире, где
поддержание бесплатно. Решение владельца — умолчания не подкручивать, а
объявить вне окна (`docs/FINDING-143.md`, раздел «Решение владельца»): любая
будущая запись, претендующая на измерение жизни, обязана явно указать `ρ` и
показать, что он внутри окна, иначе это уровень `D`, а не результат.

### Порог вымирания на общей среде (уровень B)

Когда среда общая и у формы есть размер, та же арифметика даёт **предсказанный порог**:

```
доход урезается долей запаса f = stock/stock_max
форма платит   f·σ·p  ≥  f0 + μn + κn²/p
пик избытка    14.679  ⇒  среда кормит хоть кого-то, пока  f ≥ f0 / 14.679
```

При старте на полном запасе первый шаг потребления оставляет `f = 0.760`, поэтому `f0 = 12` требует
`0.817` и **гибнет на шаге 1**, а `f0 = 11` требует `0.749` и живёт: **24 из 24 прогонов против 0 из
24**. Та же формула предсказала пороги для других стартовых форм (клетка 6.975, 2×2 11.8, 3×3 14.3) —
наблюдено 8, 11, 12. Источник: находки 219, 226, 227, 229; в статье — §4.7.

## Чего в модели нет

Этот раздел — не список планов, а границы применимости всего, что выше.

| отсутствует | следствие |
|---|---|
| **производство** | система не производит то, из чего состоит; организация задана извне |
| **граница как состояние** | `structure` удалён 2026-11-14: он был равен `1 − damage` и не добавлял условия смерти |
| **отходы и круговорот вещества** | вещество берётся из клетки, но не возвращается в неё в изменённой форме |
| **наследование организации** | размножение есть, но выключено по умолчанию (`birth_threshold = INFINITY`, `max_population = 0`); ребёнок копирует политику родителя, и **вариация есть** — `Life::set_policy_mutation` (0.27 — нейтраль, `docs/FINDING-221.md`), но наследуется **политика**, а не организация: генома нет |
| **ремонт второго порядка** | урон не разрушает способность чинить |
| **пространство конфигураций в основном мире** | формы с частями есть, но **отдельным миром** (`core/src/form.rs`, `core/src/shape_world.rs`, `docs/FINDING-215.md`), не внутри `Life`; в основном мире организм — точка |
| **восприятие области** | чтение **платное** (`World::read_cost`, `docs/FINDING-167.md`) и **широкое** (`Life::set_sight_radius(k)`, `docs/FINDING-208.md`), но форма видит **окно вдоль линии**, а не область: «своё место» и «поиск» невыразимы (`docs/WHERE-WE-ARE.md`, ограничение 2) |

**Движок есть. Слона в нём пока нет.**

## Модель

### Организм

`Organism` (`core/src/organism.rs`) — энергия и урон; урон в `[0, 1]`, энергия
в `[0, capacity]`. Шаг (`Organism::step`, `core/src/organism.rs:418`):

1. **доход** — берётся `min(income, доступно в клетке)`;
2. **содержание** — вычитается `maintenance_cost`;
3. **урон** — прибавляется `damage_rate`, ограниченный единицей;
4. **починка** — по стратегии `RepairPolicy`: `AllOrNothing` (умолчание,
   историческое поведение) — если `damage · repair_cost < energy`, платится вся
   цена и урон обнуляется, иначе урон переживает шаг; `Proportional` — чинится
   столько, сколько куплено, резерв на это и тратится; `None` — не чинится
   вовсе. Стратегию выбирает `step_with(world, resource, policy)`;
5. **потолок** — применяется последним, после всех платежей;
6. **смерть** — `energy ≤ 0` или `damage ≥ 1`.

Урон **суммарный**, а не по участкам. Модель «у урона есть место» (8 участков,
политики `worst` / `round` / `cheapest`) существует только в макете
`docs/FINDING-143.md` и в `core` не перенесена — выводы макета про политики
починки на `core` **не переносятся**. Стратегии `RepairPolicy` решают другой
вопрос — **когда и сколько** платить за починку суммарного урона, а не **что**
чинить первым. `step` — это `step_with(..., AllOrNothing)`, поэтому ни один
прежний прогон и ни один хеш динамики не сдвинулся.

### Среда

`Field` (`core/src/field.rs`) — одномерное пространство из клеток. Клетка
восстанавливается по закону выше; организм за шаг просит `t`, забор
последовательный. Перемещение имеет энергетическую стоимость.

### Политики

`Policy` (`core/src/life.rs:47`):

| политика | что делает |
|---|---|
| `Stay` | стоит на месте |
| `Random` | ходит случайно |
| `Remember` | запоминает самую богатую из посещённых клеток; **одноразовый выбор**, после прибытия память не меняется |
| `Memory` | держит лучшую увиденную клетку и обновляет память каждый шаг, включая стоянку на ней |
| `Sighted` | смотрит на двух соседей и идёт к более богатому; первая политика с обратной связью от мира |

Все политики фиксированы — это не обучение. Их назначение: измерить, как
наличие действия и индивидуальной истории меняет динамику в одной и той же среде.

### Параметры мира

`World` (`core/src/organism.rs:208`) — `income`, `maintenance_cost`,
`repair_cost`, `damage_rate`, `capacity`, `read_budget`, `share`
(`Sequential` / `Proportional`), `tiebreak` (`Left` / `Random`), `look_order`
(`LookThenEat` / `EatThenLook`). Каждый параметр, который может изменить
динамику, входит в хэш трассировки — иначе два плеча выглядели бы как одно.

### Мир форм (отдельно от `Life`)

Чтобы форма могла иметь части — а без этого структуру нельзя ни выбрать, ни измерить — рядом с
`Life` живёт второй, маленький мир: `Form` (`core/src/form.rs`) и `ShapeWorld`
(`core/src/shape_world.rs`). Он **не участвует** ни в одном записанном прогоне: `hash_golden`
проходит, все числа 176–229 получены независимо друг от друга.

| понятие | что это | где |
|---|---|---|
| `Form` | связный набор клеток; `cells()` и `perimeter()` считаются из геометрии, а не задаются | `core/src/form.rs` |
| `ShapeEconomy` | `доход = σ·p`, `расход = fixed_cost + μn + κn²/p` | `core/src/form.rs` |
| `fixed_cost` | плата за форму, не за клетку; задаёт **интервал** размеров | `docs/FINDING-219.md` |
| `Pool` | общий запас, который формы делят: доход урезается долей `stock/stock_max` | `docs/FINDING-218.md` |
| `birth_cost_per_cell` | рождение стоит пропорционально размеру ребёнка | `docs/FINDING-223.md` |

Арифметика этого мира даёт **предсказанный порог вымирания** (см. раздел выше), а его главный
отрицательный результат назван прямо: **платёжеспособность не равна приспособленности** — интервал
говорит, кто может жить, а отбор следует числу потомков (`docs/FINDING-222.md`).

### Наблюдение

Прогон пишется в JSON (`core/src/trace.rs`). На шаг на организм: клетка,
энергия, урон, живость, содержимое памяти, направление, взятое из клетки,
откуда пришёл. Плюс `policy`, `seed`, `read_budget`, `share`, `tiebreak`,
`look_order` и **хэш динамики** (FNV-1a по битовым представлениям всех
записанных чисел). Хэш — отпечаток, а не криптографическая гарантия; его задача
— сделать «два плеча, которые на самом деле одно плечо» незаметным невозможно.

Наблюдатель не участвует в вычислении следующего состояния и не передаёт
системе результаты измерений (`core/src/probes.rs`, `checks/observe_vs_act.py`).

## Уровни доказательности

| уровень | смысл | инструмент |
|---|---|---|
| **A** | доказано формально | Lean 4, Verus |
| **B** | проверено на конкретных входах | Rust-тесты |
| **C** | измерено в симуляции | Python, JavaScript |
| **D** | гипотеза, не проверена | — |

Уровни не смешиваются и не подменяют друг друга. `A` не следует из `B`, `B` не
следует из `C`.

- Компилирующаяся теорема не гарантирует, что утверждение сформулировано верно.
- Успешный тест не доказывает закон.
- Численный результат не доказывает причинную связь.

Отдельно от уровня стоит **исход проверки** — пять исходов, а не два
(`PROTOCOL.md` §4): проверка сработала (`passed`), не сработала (`failed`),
не смогла различить (`void`), плечи неразличимы по построению
(`insensitive by construction`), вопрос в мире не стоит (`not applicable`).
Проверка, которая не может провалиться, — не проверка.

### Rust

`core/` — исполняемое ядро. Ошибки, найденные в проекте, были механическими, и
у каждой механической ошибки есть форма, которую может запретить тип: `Fold`
нельзя собрать с неверным периодом, `Chi2` носит свои степени свободы,
`Mean` и `Spread` — разные типы, `Converged` выдаёт только тест на сходимость
(`core/src/lib.rs`). Чего типы не могут — проверить, что **вопрос поставлен
верно**; это ловят контрпримеры и симуляция.

### Rust ↔ Lean

Экспериментальный мост через C FFI (`core/src/bridge.rs`, `laws/Legacy/FFI.lean`):
отдельные функции, определённые в Lean, вызываются из Rust и сравниваются с
исполняемой моделью. Полной эквивалентности ядра и спецификации нет и не
заявляется. Если Lean или его библиотеки недоступны, `core/build.rs` собирает
заглушку — ядро соберётся, но проверки настоящего моста будут недоступны
(`checks/stub_covers_bridge.py` следит, чтобы заглушка не выдавала себя за мост).

### Verus

`verus/integer_laws.rs` — формальная проверка отдельных целочисленных функций и
их соответствия спецификациям с явно заданными ограничениями.

### Численные проверки

`checks/` — независимые проверки формул, граничных условий, контрпримеров и
результатов моделирования. Отрицательные результаты сохраняются наравне с
положительными (`docs/ELIMINATED.md`). Контракт результатов — `checks/contract.py`:
неразбираемый файл прогона — нарушение контракта, а не пропуск.

## Быстрый старт

Всё собирается и запускается в **WSL/Linux**. На Windows линковка Rust с Lean
сломана (`undefined reference to GetHostNameW`), поэтому `cargo build` там
падает.

### Требования

- Rust и Cargo;
- Lean 4 через Elan;
- GCC для сборки C FFI;
- Python 3;
- Node.js для JavaScript-проверок;
- Verus и Z3 для формальной проверки `run.sh all`.

Версия Lean фиксирована в `laws/lean-toolchain`.

### Получение проекта

```bash
git clone https://github.com/mak777uh/marfagenez.git
cd marfagenez
```

### Всё сразу

```bash
bash run.sh          # все проверки: тесты, Lean, эксперименты, Verus
bash run.sh test     # только тесты Rust
bash run.sh lean     # только сборка Lean
bash run.sh exp      # только эксперименты
bash run.sh reach    # только достижимость файлов Lean
```

Правило всего скрипта: **вывод фильтруется для человека, код возврата берётся
от проверки.** Конвейер не может стоять последним, если его хвост (`head`,
`tail`, `awk`, `grep`) возвращает 0 независимо от результата.

### По отдельности

```bash
# тесты Rust; --test-threads=1 обязателен: Lean runtime не потокобезопасен
cargo test --manifest-path core/Cargo.toml --release --tests -- --test-threads=1

# математика
cd laws && lake build && lake build Legacy && cd ..

# демонстрационный прогон первоначальной модели
cargo run --manifest-path core/Cargo.toml --release --bin run

# модель организмов с записью трассировки
cargo run --manifest-path core/Cargo.toml --release --bin trace -- \
  --policy memory --steps 2000 --every 20 --seed 20250101
```

Параметры `trace`:

| аргумент | назначение |
|---|---|
| `--policy` | `stay`, `random`, `remember`, `memory`, `sighted` |
| `--steps` | число шагов |
| `--every` | частота записи кадров |
| `--seed` | начальное значение генератора |
| `--n` | число организмов |
| `--cells` | число клеток среды |

Результаты пишутся в `results/`.

### Отдельные проверки

```bash
python3 checks/contract.py        # контракт файлов прогона
python3 checks/observe_vs_act.py  # наблюдение не меняет динамику
python3 checks/reach.py --strict  # достижимость файлов Lean
node checks/verify_all.js
node checks/audit.js
```

У каждой проверки своя область применимости. Результаты и их ограничения —
в `docs/`.

## Как читать результаты

1. **Сначала `ρ` и `ρ_s`.** Если запись претендует на измерение жизни, в ней должен быть
   указан `ρ_s = damage_rate · repair_cost / (income − maintenance)` — окно против **избытка**, а не
   против дохода: `ρ` по доходу пропускает смертельные миры (`income = 1.0`, `maintenance = 0.99`
   даёт `ρ = 0.015` «в окне» при нулевом избытке). `ρ` по доходу остаётся для совместимости, но
   критерием не является; при `income − maintenance <= 0` окна нет вовсе. Диагностика:
   `python3 checks/rho_surplus.py`. И показано, что он внутри
   окна. Иначе это измерение движения, памяти или дележа.
2. **Смотрите на границу применимости.** Формула без границы — половина записи.
   В `POSITIVE.md` граница — обязательное поле.
3. **Проверяйте уровень.** `A` — доказано, `B` — проверено на входах, `C` —
   измерено в симуляции, `D` — гипотеза. Уровни не складываются.
4. **Различайте исход и статус.** `void` и `not applicable` — не то же самое,
   что `failed`, и не то же самое, что `passed`.
5. **Не читайте отрицательный результат как провал.** Он записан, потому что
   сужает пространство поиска. Это и есть результат.
