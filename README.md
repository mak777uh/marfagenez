# MARFAGENEZ

**Исследование искусственной среды, в которой могут возникать, поддерживаться и развиваться автономные формы жизни.**

Marfagenez — экспериментальный исследовательский проект на пересечении искусственной жизни, математического моделирования, формальной верификации и вычислительных экспериментов.

Цель проекта — разобраться в минимальных условиях, при которых искусственная система способна существовать в изменяющейся среде, поддерживать собственную организацию, использовать ресурсы, сохранять информацию об опыте и формировать поведение.

Проект развивается от первых принципов. Мы не задаём заранее конечную форму организма или желательное поведение. Вместо этого исследуем механизмы, ограничения и закономерности, из которых могут возникать более сложные формы организации.

**Это исследование, а не готовый продукт или образовательная система.**

---

## Исследовательский вопрос

Какие свойства среды и какие механизмы взаимодействия позволяют искусственной системе:

- поддерживать собственную организацию;
- получать и расходовать ресурсы;
- сохранять устойчивость при воздействии внешних условий;
- изменять поведение на основании собственного опыта;
- восстанавливаться после повреждений;
- влиять на условия собственного дальнейшего существования?

Важная часть исследования — не программировать заранее требуемый результат.

Мы хотим понять, какие свойства возникают из самой динамики системы, а какие приходится искусственно навязывать правилами.

Рост сложности, продолжительность жизни, численность популяции и разнообразие сами по себе не считаются доказательством успешного развития. Это наблюдаемые характеристики, а не заранее установленные цели.

## Основные принципы

**1. Не задавать конечную форму.**

Не программировать, каким именно должен стать организм. Реализовывать базовые механизмы и наблюдать, какие структуры и формы поведения они допускают.

**2. Разделять наблюдение и воздействие.**

Измерительный механизм не должен незаметно менять исследуемую динамику. Наблюдатель находится за пределами моделируемой среды.

**3. Не путать существование с жизнью.**

Наличие состояния или движение случайных точек ещё не означает наличие организма. Для исследования жизни необходимы дополнительные механизмы: ресурсы, затраты, поддержание структуры, повреждения и возможность смерти.

**4. Не принимать предположения за результаты.**

Каждое утверждение должно иметь понятный статус: математически доказано, проверено на конкретных входах, измерено экспериментально или пока остаётся гипотезой.

## Архитектура

Проект разделяет исследование на несколько взаимосвязанных, но логически самостоятельных уровней.

| Уровень | Назначение | Инструменты |
|---|---|---|
| Математические законы | Формализация свойств моделей | Lean 4, Mathlib |
| Исполняемая среда | Реализация динамики и организмов | Rust |
| Формальная проверка | Проверка отдельных вычислительных свойств | Lean, Verus |
| Эксперименты | Численные проверки, контрпримеры, сравнения | Python, JavaScript |
| Наблюдение | Запись состояния и динамики системы | JSON, Rust |
| Анализ | Интерпретация результатов и ограничений | Исследовательская документация |

### 1. Математическая модель

В проекте сохраняется первоначальная модель ограниченного пространства.

Организмы в ней представлены векторами характеристик:

\[
X \in \mathbb{R}^{d}
\]

Они перемещаются под действием собственного сноса и случайного шума:

\[
x_{t+1}=R_B(x_t+\mu+\sigma\xi_t)
\]

где:

- \(B\) — граница пространства;
- \(\mu\) — направленный снос;
- \(\sigma\) — интенсивность шума;
- \(\xi_t\) — случайное возмущение;
- \(R_B\) — отображение, возвращающее состояние внутрь допустимой области.

Эта модель позволяет исследовать влияние геометрии, границ, распределений, шума и динамических ограничений.

Она не является полноценной моделью организма. Это математический фундамент и контрольная модель для последующих исследований.

Основные файлы: `laws/`, `core/src/child.rs`, `core/src/room.rs`, `core/src/cycle.rs`.

### 2. Модель организма

Следующий уровень — организм с внутренним состоянием и собственными затратами.

В текущей реализации организма присутствуют:

| Компонент | Назначение |
|---|---|
| Structure | Внутренняя организация |
| Energy | Энергетический резерв |
| Damage | Накопленные повреждения |
| Maintenance | Затраты на поддержание существования |
| Repair | Восстановление после повреждений |
| Death | Прекращение существования при исчерпании ресурсов или критическом повреждении |

В отличие от первоначальной модели, организм здесь способен умереть.

### 3. Среда и ресурсы

Среда представлена одномерным пространством из ячеек, каждая из которых содержит определённый запас ресурса.

Ресурс может расходоваться и восстанавливаться.

Организм может оставаться на месте или перемещаться между ячейками. Перемещение имеет энергетическую стоимость.

Это позволяет исследовать связь между доступностью ресурсов, поведением, затратами и выживанием.

### 4. Память и поведение

В проекте реализованы первые варианты поведения:

- `Stay` — оставаться на месте;
- `Random` — перемещаться случайным образом;
- `Remember` — запоминать наиболее богатую из посещённых ячеек и возвращаться к ней.

Это фиксированные политики, а не обучающиеся нейронные сети.

Их назначение — исследовать, как наличие действия и индивидуальной истории меняет динамику организма в одной и той же среде.

Основные файлы нового цикла: `core/src/organism.rs`, `core/src/field.rs`, `core/src/memory.rs`, `core/src/life.rs`.

### 5. Наблюдение и воспроизводимость

Прогон можно записать в виде JSON-трассировки.

Для каждого организма сохраняются:

- положение;
- энергия;
- повреждения;
- состояние жизни;
- содержимое памяти;
- направление движения;
- полученный ресурс.

Каждая трассировка дополнительно содержит идентификатор политики, seed и хэш динамики.

Это позволяет сравнивать прогоны и обнаруживать случаи, когда два экспериментальных условия фактически воспроизводят одну и ту же динамику.

Хэш используется как отпечаток состояния, а не как криптографическая гарантия.

Наблюдатель не участвует в вычислении следующего состояния и не передаёт системе результаты измерений.

## Формальная верификация и проверка

Для проекта принципиально важно различать доказательства свойств математической модели и проверку исполняемой программы.

Используются четыре уровня свидетельств.

| Уровень | Смысл | Метод |
|---|---|---|
| **A — Formal** | Утверждение доказано в формальной системе | Lean 4, Verus |
| **B — Tests** | Реализация проверена на конкретных входах | Rust tests |
| **C — Experiments** | Получены численные результаты | Python, JavaScript |
| **D — Hypotheses** | Утверждение пока не проверено | Исследовательская гипотеза |

Эти уровни нельзя подменять друг другом.

Компилирующаяся теорема не гарантирует, что исходное утверждение правильно сформулировано. Успешный тест не доказывает математический закон. Численный результат не доказывает причинную связь.

### Lean 4

Директория `laws/` содержит формализацию математических свойств исследуемых моделей.

Используются Lean 4 и Mathlib с зафиксированными версиями:

- Lean: `4.36.0-rc2`;
- Mathlib: зафиксированная ревизия в `laws/lake-manifest.json`.

### Rust

Директория `core/` содержит исполняемое ядро.

При разработке используются типы и ограничения конструкторов, чтобы исключать некоторые некорректные состояния непосредственно на уровне программы.

### Rust ↔ Lean

В проекте реализован экспериментальный мост через C FFI.

Он позволяет вызывать отдельные функции, определённые в Lean, из Rust и сравнивать их результаты с исполняемой моделью.

Полноценное доказательство эквивалентности всего Rust-ядра и математической спецификации пока не достигнуто.

### Verus

В `verus/` исследуется формальная проверка отдельных целочисленных функций и их соответствия спецификациям с явно заданными ограничениями.

### Численные проверки

В `checks/` находятся независимые проверки формул, граничных условий, контрпримеров и результатов моделирования.

Отрицательные результаты сохраняются наряду с положительными.

Подробная карта утверждений и их статусов: [`docs/CLAIMS.md`](docs/CLAIMS.md).

## Быстрый старт

### Требования

- Rust и Cargo;
- Lean 4 через Elan;
- GCC для сборки C FFI;
- Python 3;
- Node.js для JavaScript-проверок.

Для математической сборки используется зафиксированный файл `laws/lean-toolchain`.

### Получение проекта

```bash
git clone https://github.com/mak777uh/marfagenez.git
cd marfagenez
```

### Сборка и тесты Rust

```bash
cargo test --manifest-path core/Cargo.toml --release -- --test-threads=1
```

Однопоточный режим важен при использовании Lean runtime в тестах.

Если Lean или необходимые библиотеки отсутствуют, `build.rs` может собрать заглушку FFI. В таком случае Rust-ядро может собраться, но проверки настоящего Lean-моста будут недоступны.

### Сборка математической части

```bash
cd laws
lake build
cd ..
```

При первой сборке может потребоваться загрузка и компиляция Mathlib.

### Запуск базовой модели

```bash
cargo run --manifest-path core/Cargo.toml --release --bin run
```

Это демонстрационный прогон первоначальной математической модели.

### Запуск модели организмов

```bash
cargo run --manifest-path core/Cargo.toml --release --bin trace -- \
  --policy remember \
  --steps 2000 \
  --every 20 \
  --seed 20250101
```

Другие политики:

```bash
cargo run --manifest-path core/Cargo.toml --release --bin trace -- \
  --policy stay --steps 2000 --every 20

cargo run --manifest-path core/Cargo.toml --release --bin trace -- \
  --policy random --steps 2000 --every 20
```

Поддерживаемые параметры:

| Аргумент | Назначение |
|---|---|
| `--policy` | `stay`, `random`, `remember` |
| `--steps` | Количество шагов |
| `--every` | Частота записи кадров |
| `--seed` | Начальное значение генератора |
| `--n` | Количество организмов |
| `--cells` | Количество ячеек среды |

Результаты записываются в `results/`.

### Дополнительные проверки

```bash
python3 checks/box_measure.py
python3 checks/observe_vs_act.py

node checks/verify_all.js
node checks/audit.js
```

Каждая проверка имеет собственную область применимости. Результаты отдельных экспериментов и их ограничения описаны в `docs/`.
