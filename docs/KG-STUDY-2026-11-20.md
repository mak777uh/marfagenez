# KG-STUDY-2026-11-20.md — научная память в репозитории: что есть, что берём, что строим

**Дата:** 2026-11-20. **Задача:** выбрать метод ведения научных заметок и связей внутри репозитория — так, чтобы было
удобно **агенту**, а не человеку. **Основание:** разбор владельцем существующих систем (OpenAlex, OpenAIRE, ORKG,
SciX Agent, OpenArx, ClaimRxiv, EVI, GraphRAG, LightRAG, HippoRAG 2).

---

## 1. Что уже есть и что из этого следует

| система | единица | что даёт | чего не даёт |
|---|---|---|---|
| **OpenAlex** (~320 млн работ) | публикация | граф цитирований, авторы, темы; MCP-интерфейс | **не** знает «A опровергает утверждение B» |
| **OpenAIRE Graph** | публикация + данные + ПО + проект | цепочка «статья → данные → код → проект» | то же: содержание не главный объект |
| **ORKG** | вклад работы (метод/данные/результат) | сравнимые описания вкладов, SPARQL | не полный граф и зависит от ручной структуризации |
| **SciX Agent** | корпус NASA ADS + MCP | 15 инструментов, PageRank/HITS/Leiden, working sets | узкая область (физика, астрономия) |
| **OpenArx** (alpha) | **утверждение** | типы связей `support/refute/qualify/extend/…`, MCP | alpha, API меняется, требует токена |
| **ClaimRxiv** (концепция, 2026) | **утверждение** | схема: assertion + evidence + **context** + provenance + epistemic status + отношения | **не реализовано**, это предложение |
| **EVI / PROV-O** | происхождение доказательства | формальная онтология: claim, evidence graph, experiment, dataset | биомедицинский уклон, не база |
| **GraphRAG / LightRAG / HippoRAG 2** | фрагменты + граф | многоуровневые резюме, обход графа, обновление | это **retrieval**, а не память знания |

**Вывод из изучения.** Все большие системы — **графы публикаций**. Единица «утверждение с контекстом, свидетельством
и статусом» существует только как **концепция** (ClaimRxiv) и как **alpha-проект** (OpenArx). Готовой, зрелой,
универсальной системы нет; это признаётся как отдельная нерешённая задача.

---

## 2. Что берём (не изобретаем)

1. **Единица знания — утверждение, а не файл** (ClaimRxiv, OpenArx).
2. **Контекст — отдельный объект**, а не фраза в тексте: два «противоречащих» утверждения могут быть непротиворечивы
   при разных условиях (ClaimRxiv).
3. **Происхождение — отдельная ось от эпистемического статуса** (EVI/PROV-O):
   `extracted` → `verified_agent` → `human_confirmed`, и **отдельно** `hypothesis / established / contested /
   replicated / refuted / bounded`.
4. **Типы отношений фиксированы**: `supports`, `refutes`, `qualifies`, `extends`, `replicates`, `supersedes`,
   `same_as`, `shared_evidence`.
5. **Доступ агента — через операции, а не через контекст**: `map`, `find`, `expand`, `contradictions`, `trace`, `add`
   (как в SciX/OpenArx MCP, но локально).
6. **Граф не загружается целиком в контекст**: в контексте — карта, текущий срез и окружение на N шагов (GraphRAG).

## 3. Чего **не** берём

1. Neo4j/векторные БД: у нас Markdown-репозиторий и гейт, лишняя инфраструктура.
2. Внешние API как основу: ключи и лимиты; наш граф должен работать **офлайн**.
3. Автоматическое извлечение утверждений из PDF: у нас **свой** корпус, извлекать нечего.

---

## 4. Решение: `kg/` — граф утверждений, append-only

### 4.1. Формат

- **Источник истины:** `kg/claims.jsonl` — **одно утверждение = одна строка JSON**, файл только дополняется.
- **Человеческое представление:** `kg/INDEX.md` — генерируется из JSONL, править руками нельзя.
- **Машина:** `kg/graph.json` — узлы + рёбра, генерируется.
- **Код:** `kg/kg.py` — валидация, генерация и запросы (CLI).

Почему JSONL, а не Markdown: агент **читает и пишет построчно**, конфликтов слияния меньше, парсинг без библиотек,
каждая строка — законченный объект. Markdown остаётся для **чтения** (генерация `INDEX.md`), но не является единицей.

### 4.2. Схема утверждения

```json
{
  "id": "C-001",
  "text": "…формулировка, проверяемая…",
  "context": {"scope": "…", "parameters": "…", "conditions": "…"},
  "epistemic": "established | hypothesis | contested | replicated | refuted | bounded",
  "provenance": "extracted | verified_agent | human_confirmed",
  "evidence": [{"kind": "experiment|literature|formula|result", "ref": "EXP-…|L-…|F-…", "strength": "…"}],
  "relations": [{"type": "supports|refutes|qualifies|extends|replicates|supersedes|same_as|shared_evidence",
                 "target": "C-…", "note": "…"}],
  "created_at": "2026-11-20",
  "updated_at": "2026-11-20"
}
```

**Правила:** `id` не переиспользуется; удаление невозможно (только `supersedes` + статус); у каждого утверждения есть
**контекст**; `provenance = extracted` **не** даёт права ссылаться на утверждение как на факт.

### 4.3. Операции (CLI, для агента)

| команда | что делает |
|---|---|
| `python3 kg/kg.py map` | карта: сколько утверждений по статусам, топ связей |
| `find <слово>` | поиск утверждений по тексту/контексту |
| `show C-00N` | утверждение с доказательствами и связями |
| `expand C-00N [N]` | окружение на N шагов |
| `contradictions` | пары `refutes` с общим контекстом; пары «одинаковый текст, разный статус» |
| `trace C-00N` | путь от утверждения к Evidence/литературе |
| `add` | добавить утверждение (валидирует схему) |
| `build` | пересобрать `INDEX.md` и `graph.json` |

## 5. Что связываем с уже существующим

| наш объект | как входит в граф |
|---|---|
| `L-NNN` (литература) | `evidence.kind = "literature"` |
| `F-NNN` (формулы) | `evidence.kind = "formula"` |
| `EXP-…` в `results/` | `evidence.kind = "experiment"` |
| `FINDING-NNN` | `evidence.kind = "result"` |
| `P-NNN` (предсказания) | отдельный тип связи `predicted_by` (расширение) |

Так граф **не дублирует** реестр, а **связывает** его: литература и прогоны остаются на своих местах, утверждения —
слой над ними.

5. Связь с внешними графами (OpenAlex MCP) — **только** для проверки библиографии, не как хранилище.
