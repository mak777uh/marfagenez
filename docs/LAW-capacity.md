# ЗАКОН ЁМКОСТИ — выведен и проверен 2026-11-13

## Что это

Сколько организмов может жить на одной клетке. Не подбор, а вывод из кода
`core/src/field.rs` (`take`, `regrow_all`) и `core/src/organism.rs` (`step`).

## Обозначения

| символ | что | откуда |
|---|---|---|
| `M` | потолок клетки (`max_resource`) | `Field::alternating(cells, rich, poor, r)` |
| `r` | скорость восстановления | там же |
| `t` | `income` — сколько организм просит за шаг | `World.income` |
| `m` | `maintenance_cost` | `World.maintenance_cost` |
| `bill` | `damage_rate * repair_cost` | 0.02 * 1.5 = **0.030** |
| `need` | `m + bill` — сколько нужно, чтобы не умереть | |
| `k` | число организмов на клетке | |

## Механика (три факта из кода)

1. **Взятие ограничено доходом, а не клеткой.**
   `core/src/organism.rs:165`: `let taken = resource.max(0.0).min(world.income);`
   Организм никогда не берёт больше `t`, даже если в клетке больше.

2. **Порядок шага** (`organism.rs:159-197`):
   income → maintenance → damage → repair → `energy.min(capacity).max(0.0)`
   → structure → смерть (`energy<=0 || structure<=0 || damage>=1`).

3. **Восстановление дважды за шаг.** `Life::advance` (`core/src/life.rs:252`):
   `if feed { regrow_all() }` → шаг каждого организма → `if !feed { regrow_all() }`.
   При `feed=false` (по умолчанию) восстановление идёт в конце шага и в начале
   следующего — то есть дважды.

## Уровень клетки в равновесии

Пусть `L` — уровень, `paid = min(k*t, L)` — сколько клетка отдала за шаг.

```
L_next = (L - paid) + (M - (L - paid)) * r
```

**Недонасыщенный режим** (`k*t <= L`):

```
L* = M - k*t*(1-r)/r
```

Самосогласован, когда `k*t <= L*`, то есть `k*t <= M*r`.

**Насыщенный режим** (`k*t >= L`): клетка отдаёт всё, что имеет, и
`L_next = M*r`:

```
L* = M*r
```

Самосогласован, когда `k*t >= M*r`.

Обе ветви сходятся при `k*t = M*r`, где `L* = M*r`. Значит

```
L*(k) = max( M - k*t*(1-r)/r ,  M*r )
```

## Условие выживания

**Недонасыщенный** (`k*t <= M*r`): каждый получает ровно `t` (клетка держит
`L* >= k*t`). Выживает, если

```
t > m + bill
```

— **не зависит от k**. Значит при таком `t` влезает любое `k`, лишь бы `k*t <= M*r`:

```
k_max = floor(M*r / t)
```

**Насыщенный** (`k*t >= M*r`): клетка платит `M*r` всего, по порядку. Последнему
достаётся `M*r - (k-1)*t`. Все живы, если

```
M*r - (k-1)*t > m + bill
k <= floor( (M*r - m - bill) / t ) + 1
```

## Итоговая формула

```
k_max(t) = max( floor(M*r/t) ,  floor((M*r - m - bill)/t) + 1 )
```

при `t > m + bill`; иначе `k_max = 0`.

Вторая ветвь действительна только если `k*t >= M*r` — иначе она описывает
несуществующий режим. На практике надо брать ту ветвь, которая
самосогласована, и брать максимум по действительным.

## Где формула отказывает — и почему это правильно

При `m = 0.8` формула даёт `t* = 0.77`, но насыщенный режим требует `t >= 0.80`.
Ветвь недействительна, значит **crowd 2 невозможен ни при каком t**. Измерено:
crowd 0 везде до 0.77, crowd 1 с 0.85. Совпадает.

То же для `m = 1.0` (`t* = 0.57 < 0.80`) и `r = 0.5` (`t* = 0.47 < 0.50`).

## Что это НЕ доказывает

- Только `Policy::Stay`. Движущиеся политики меняют, кто на клетке.
- Только равновесие после 5000 шагов. Переходные процессы (первые ~400 шагов)
  дают другие числа — например crowd 3 при 300 шагах.
- `e0 = 10.0`. При меньшем стартовом запасе организмы могут не дожить до
  равновесия.
- Непрерывная модель. Дискретность (`floor`) проверена только в точках выше.
- Не объясняет, почему при income=1.0733 ровно на границе получается 60 при
  5000 шагах и 40 при 20000 — граница бистабильна, это отдельный вопрос.
- `bill = damage_rate * repair_cost` предполагает, что ущерб всегда
  полнoстью оплачивается. Если энергии не хватает на ремонт, `bill` меньше —
  не проверено.

## Формализация в Lean

`laws/Medium/Capacity.lean`, раздел после `rationed_take_above_maintenance`.
Собрано 2026-11-13: `lake build` — 0 ошибок, 55 файлов, 265 теорем, 0 `sorry`.

| теорема | что говорит |
|---|---|
| `cellLevel` | `max(M - k*t*(1-r)/r, M*r)` — обе ветви одним `max` |
| `cellLevel_eq_cStar` | недонасыщенная ветвь = старый `cStar` (нужно `r ≤ 1`) |
| `saturated_level` | насыщенная ветвь даёт ровно `M*r` |
| `branches_meet` | ветви сходятся при `k*t = M*r` |
| `unsaturated_count` | ниже насыщения каждый получает свой `t` |
| `saturated_last_take` | последний берёт `M*r - (k-1)*t` |
| `saturated_count_iff` | этот остаток покрывает `need` ⟺ `k-1 < (M*r - need)/t` |
| `capacity_law` | `floor(M*r/t)` не перебирает; последний остаток `≥ need` |
| `capacity_law_strict` | ещё один организм перебирает (нужно `0 ≤ need`) |

### Ошибка, которую поймала формализация

`capacity_law` сначала была записана со строгим `<` на насыщенной ветви:

```
need < M*r - floor((M*r - need)/t) * t
```

**Это ложь.** Контрпример: `M*r = 10, need = 4, t = 2`. Тогда
`floor((10-4)/2) = 3` и `10 - 3*2 = 4 = need`, значит `4 < 4` — неверно.
Ложность возникает ровно когда `(M*r - need)/t` целое.

Правильная формулировка: нестрогое `≤` в `capacity_law`, а строгость —
на шаг дальше, в `capacity_law_strict`:

```
0 < M*r - (floor((M*r - need)/t) - 1) * t
```

Это и есть содержательное утверждение «`floor+1` перебирает»: последний
организм получает `≥ need`, а добавка ещё одного съедает `t` сверх.

Строгая версия требует `0 ≤ need`. Без него `M*r - p + t > 0` не следует:
из `p ≤ M*r - need` получаем `M*r - p ≥ need`, но если `need < 0`, то
`M*r - p + t` может быть отрицательным при достаточно большом `t`.
