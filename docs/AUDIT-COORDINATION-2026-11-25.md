## 1. Что за проект (минимум контекста)

Исследовательский репозиторий: одна научная линия («какой темп процесса решает, выживет ли система»),
две карты знаний, экспериментальная часть на Rust, формальные доказательства на Lean, десятки проверок.

| часть | путь | размер |
|---|---|---|
| литературная карта (ячейки с цитатами и числами) | `literature/map/` | ~1000 ячеек |
| карта знаний (наши утверждения, формулы, прогоны) | `kg/` | ~580 узлов |
| эксперименты | `core/` (Rust), результаты в `results/` | 407 прогонов |
| формальные доказательства | `laws/` (Lean) | 64 файла |
| проверки | `checks/` | 51 проверка |
| гейт | `bash run.sh all` | **15+ минут**, дорого |

Проверки делятся на **точечные** (секунды: `checks/map_contract.py`, `checks/doc_links.py`,
`checks/log_check.py`) и **полный гейт** (`run.sh all`).

## 2. Задача координации

В одном каталоге `/root/marfagenez` (WSL) работают **два, позже три** исследовательских агента:

- `main` — основной, **единственный, кто делает git** (commit, push);
- `fast` — быстрый партнёр, git не использует;
- возможно `third`.

Они равноправны в исследовательских решениях и в управлении очередью, но неравноправны в публикации.

**Ограничения среды:**

- общий каталог на одной машине (WSL), путь через `\\wsl.localhost\` медленный и ненадёжный — запрещён;
- git-операции только у `main`;
- полный гейт дорогой, поэтому его нельзя гонять на каждый шаг;
- часть файлов — «зона контракта»: их правка ломает инварианты (см. §4).

## 4. Как система работает сейчас (сводка)

### 4.1. Каталоги

```
.coord/
  README.md                  правила
  agents/<name>.md           регистрация
  pending/<ID>/TASK.md       свободная задача (менять можно)
  active/<ID>/TASK.md        взятая: НЕИЗМЕНЯЕМА (sha256 в .claim.json)
  active/<ID>/RESULT.md      результат (пишет исполнитель)
  active/<ID>/DONE.json      заявка о завершении: артефакты + проверки
  completed/<ID>/...         закрытые (переносит main после проверки)
  events/<ts>-<agent>.md     журнал событий
  standing/*.md              тексты постоянных задач
```

### 4.2. Инструмент `tools/coord.py`

| команда | что делает | атомарность |
|---|---|---|
| `add` | создать свободную задачу (`--kind research|request|maint`, `--standing`) | — |
| `take ID --agent X` | взять: `os.mkdir(active/<ID>)`; sha256 карточки; запись `.claim.json` | **mkdir атомарен**, второй получит `FileExistsError` |
| `finish ID --agent X` | заявка: проверяет, что `TASK.md` не менялся, что есть `RESULT.md`, пишет `DONE.json` | — |
| `verify ID` | прогоняет `accept`-команды из карточки | — |
| `close ID` | `active/` → `completed/` | — |
| `stale` | задачи старше TTL (180 мин) | — |
| `release ID --agent X` | вернуть в `pending` (раунды постоянных задач удаляются) | — |

**Проверки при взятии:** пересечение рабочей области с активными задачами (по префиксу каталога и
glob-префиксу); защищённые зоны (`core/`, `laws/`, `verus/`, `checks/`, `run.sh`, `AGENTS.md`,
`kg/nodes.jsonl`, `kg/migrate.py`, `kg/kg.py`, `tools/coord.py`) может брать только `main`.

### 4.3. Постоянные задачи

Три задачи не закрываются никогда: каждое взятие создаёт раунд `active/<ID>-<время>/`, карточка
остаётся в `pending/`. Раунд = один инкремент: один вопрос, предсказание **до** запуска, результат с
командой, точечные проверки, `RESULT.md` + `DONE.json`.

### 4.4. Правила против потери данных (уже приняты)

1. Исходники карт не правятся напрямую: агент пишет `literature/map/inbox/<agent>-<task>.jsonl`,
   `main` импортирует штатным `tools/map_ingest.py`.
2. `kg/nodes.jsonl` только собирается (`kg/migrate.py` → `kg/kg.py build`).
3. Номера циклов в `docs/agent/AGENT_LOG.md` присваивает только `main`; агент пишет
   `JOURNAL-FRAGMENT.md`.
4. Дорогие операции (сборка эмбеддингов, `run.sh all`, пересборка `kg/`, `results/`) — только `main`.
5. `docs/*.md` — один автор за раз; чужой документ правится через задачу.
6. Запрещены не только `git add/commit/push/checkout/reset/clean/merge/rebase`, но и
   `stash/restore/switch/rm/worktree`.
7. TTL 180 минут; просроченную задачу `main` может вернуть в `pending`.

## 5. Что именно нужно от аудита

Оцени систему и предложи **конкретные изменения**. Интересует:

### 5.1. Корректность конкурентного доступа

- Достаточно ли `mkdir` как примитива блокировки на одной ФС WSL? Где остаются гонки
  (например, `add` двух задач с одним ID; `close` одновременно с `take`; `release` при живом исполнителе)?
- Нужны ли версии/поколения задач (optimistic concurrency), или файловой блокировки хватает?
- Что делать с частично записанным файлом (агент убит в середине `write`)? Нужен ли
  write-temp-then-rename везде?

### 5.2. Области ответственности (areas)

- Достаточно ли правил «пересечение по префиксу»? Где оно даст ложные срабатывания или пропустит
  конфликт (два агента в одном файле через разные glob)?
- Как лучше выражать область: glob, список файлов, «каталог целиком», префикс?

### 5.3. Проверка завершения

- Сейчас `accept` — это shell-команды из карточки. Достаточно ли? Нельзя ли «пройти» проверку,
  ничего не сделав (например, команда `true`)?
- Как автоматически связать результат с артефактами: хэши файлов, список изменённых путей?

### 5.4. Масштабирование до трёх агентов

- Что сломается при появлении третьего? Какие правила нужны дополнительно?
- Нужна ли приоритезация по «доходу на минуту» и кто её считает?

### 5.5. Постоянные задачи

- Правильно ли, что раунды — отдельные каталоги? Как нумеровать раунды и как не плодить мусор?
- Как избежать дублирования работы между «постоянными» и «плановыми» задачами?

### 5.6. Устойчивость к сбоям

- Агент умер, оставив `active/`. Как отличить «работает медленно» от «умер»?
- Нужны ли heartbeat-файлы, и как часто?
- Что делать с `results/` и общими каталогами при сбое?

### 5.7. Гигиена и наблюдаемость

- Достаточно ли `events/` для восстановления картины? Что добавить (кто что читал, кто что менял)?
- Как избежать конфликтов в `docs/agent/AGENT_LOG.md` при двух агентах?

## 6. Формат ответа

Пришли **markdown-документ** со структурой:

1. **Вердикт по каждому пункту §5** — «достаточно / недостаточно / опасно», с обоснованием.
2. **Список изменений** — по одному пункту на изменение, каждое в виде:
   - что меняем (файл и место),
   - зачем (какую гонку/потерю данных это закрывает),
   - текст правила или псевдокод (готовый к внедрению).
3. **Что НЕ надо менять** — какие текущие решения уже корректны и трогать их вредно.
4. **Три самых опасных места** в текущей системе — по убыванию риска.
5. **Минимальный набор правил для третьего агента** (если он появится завтра).

**Требования к предложениям:**

- внедряемо **без CI** и без внешних сервисов (только файлы, Python 3, bash);
- не должно требовать сетевого доступа;
- не должно ломать правило «git только у `main`»;
- предпочтение — простым механизмам (атомарные rename/mkdir, хэши, TTL), а не фреймворкам;
- если предлагаешь блокировки — укажи, что произойдёт при убитом процессе и как это лечится.

## 7. Чего в ответе быть не должно

- Общих слов «используйте очередь сообщений / брокер / базу данных»: инфраструктуры нет.
- Предложений, требующих правки `checks/` или `run.sh` ради «удобства».
- Советов «пусть агенты договариваются» — нужны механические правила.
- Отмены правила «git только у `main`».
