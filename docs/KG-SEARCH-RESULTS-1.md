## 1. Формат: OKF v0.2 — что берём

**Источники.** Спецификация: `github.com/open-knowledge-format/open-knowledge-format` (`SPEC.md`); обзор
`okf-explorer` (v0.2: trust, lifecycle, attestation); крейт `okf 0.2.7`.

**Что стандарт задаёт (по фрагментам):**

- корневой `index.md` объявляет `okf_version: "0.2"`;
- поля: `type`, `sources`, `generated`, `verified`, `status`, `stale_after`;
- `verified` — **список проверок**, каждая с `by` (например `human:eugen` или `agent:okf-pipeline`) и датой;
- **Attested Computation**: агент может подставлять **только значения объявленных параметров**, **не** писать сам
  расчёт; исполнитель связывает расчёт с параметрами, а **аттестер независимо повторяет связывание и сравнивает** —
  без LLM;
- `retrieval` **вынесен за рамки** стандарта.

**Что берём:** поля `sources / verified / status / stale_after` и идею **attested computation** — она точно
соответствует нашей связке «формула + прогон + команда».

**Что не берём:** YAML-frontmatter как единственный формат (у нас JSONL-канон), и `retrieval` (мы его строим сами).

## 2. Формулы: Content MathML и OpenMath **не конкуренты**

**Источники.** `openmath.org/om-mml`: «OpenMath is aimed at encoding the **semantics** of mathematics… MathML is aimed
at the presentation and the **content** markup»; W3C MathML 3, глава 4 (Content Markup: «explicit encoding of the
underlying mathematical meaning»); статья о переводе Content MathML ↔ OpenMath (Carlisle, Davenport и др.); SO:
«форматы очень близки и определены почти одними людьми».

**Вывод:** OpenMath — **семантика** с расширяемыми Content Dictionaries (применима к произвольной математике);
Content MathML — тоже семантика, но в XML-обёртке и с более жёсткой формализацией в MathML 3. Перевод между ними
**возможен** и описан.

**Решение для нас (K-007):**

```
канон:     LaTeX  (читаемость, diff, наши документы)
семантика: OpenMath-подобная запись в JSON (symbol, args, cd) — только для формул, которые проверяются кодом
проверка:  Lean-имя (если формализовано) или прогон (если измерено)
```

**Почему не Content MathML целиком:** XML-обёртки и словари дают вес, которого у нас нет; нам нужны **три** вещи —
читаемость, машинная однозначность (символы и арность), проверка. LaTeX + структурный JSON + Lean/прогон это покрывают.

## 3. Единицы: QUDT и UCUM — берём **коды**, не онтологию

**Источники.** QUDT (`qudt.org`): «унифицированная архитектура для количеств, типов величин, единиц, размерностей и
типов данных»; UCUM (`ucum.org`): «кодовая система для однозначной электронной передачи количеств вместе с единицами»;
статья 2025 (PMC11842773) — аннотирование метаданных онтологией единиц: `gm/m2`, `g/m^2`, `gramPerMeterSquared` — одна
и та же единица в разных записях.

**Решение для нас (K-008):**

```
units: {"D": "1", "lambda": "1/s", "delta": "1/s", "h": "1"}   ← UCUM-коды
проверка: размерностный вектор (L, M, T, …) считается из кодов; произведение по обе стороны уравнения обязано совпасть
```

**Почему UCUM:** короткие коды (`m/s`, `1/s`), машинная арифметика, без RDF. QUDT-онтологию не тянем — нам не нужны
URI на каждую единицу.

**Инцидент, который это предотвращает:** Mars Climate Orbiter (1999) — потеря аппарата из-за несовпадения единиц
(упомянуто в arXiv:2609.38242 о типизированных исчислениях единиц). Наши «невозможные числа» — тот же класс ошибки.

## 4. Lean и размерности

**Источники.** Lean-библиотека `lean-units` (определения размерностей: длина, время, масса, температура); terrytao
`Analysis/Misc/UnitsSystem` (класс `UnitsSystem` с типом `Dimensions`); обсуждение Lean 4 (dimensional analysis через
типы); arXiv:2609.38242 — исчисление единиц с конверсией.

**Вывод:** размерности **можно** выразить типами в Lean, но это отдельная библиотека и отдельная работа. Нам сейчас
достаточно **размерностного вектора в `math.units`** и проверки в Python; Lean оставляем только для теорем о законах.
