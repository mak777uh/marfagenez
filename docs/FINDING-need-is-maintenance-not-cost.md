# FINDING: `need` — что именно должен забрать организм, чтобы остаться живым

**Дата:** 2026-11-13
**Статус:** измерено; формула исправлена; теорема ещё не написана
**Файлы:** `core/src/organism.rs:159-197`, `core/src/field.rs:187-195`,
`checks/exp52_capacity_vs_income.py`, `results/EXP-52/`

---

## Что было записано неверно

В `exp52_capacity_vs_income.py` и в `LAW-capacity.md` стояло:

```
cost = maintenance + damage_rate * repair_cost = 0.6 + 0.02*1.5 = 0.63
k_max = 0 if income < cost, else 1 + floor((M*r - cost)/income)
```

Отсюда следовало, что при `income = 1.00` и `M·r = 1.6`:

```
k_max = 1 + floor((1.6 - 0.63)/1.00) = 1 + floor(0.97) = 1
```

То есть одна клетка держит одного. Измерение дало **52 живых на 40 клетках**.

## Что происходит на самом деле

`organism.rs:159-197`, порядок операций:

```rust
let taken = resource.max(0.0).min(world.income);   // 1. забрать
self.energy += taken;
self.energy -= world.maintenance_cost;             // 2. заплатить за жизнь
self.damage = (self.damage + world.damage_rate).min(1.0);   // 3. урон растёт
if self.energy > 0.0 && self.damage > 0.0 {        // 4. починиться, если есть чем
    let affordable = self.energy / world.repair_cost;
    let repaired = affordable.min(self.damage);
    self.damage -= repaired;
    self.energy -= repaired * world.repair_cost;
}
self.energy = self.energy.min(world.capacity).max(0.0);
if self.energy <= 0.0 || self.structure <= 0.0 { self.alive = false; }
```

Смерть наступает при `energy <= 0` **после** шага 4. Значит выжить в одном шаге
можно при

```
taken > maintenance
```

если `damage` уже 0 и чинить нечего. Ремонт — это **не постоянный налог**, а
плата за накопленный урон. У сытого организма `damage` каждый шаг падает до 0
(энергии хватает), и следующий шаг начинается с `damage = 0`. Поэтому

```
need = maintenance
```

а не `maintenance + damage_rate*repair_cost`. Величина `0.63` — это стоимость
**одного шага с нуля**, а не стоимость поддержания.

## Числа

`results/EXP-52/`, 40 клеток, `M = 2.0`, `r = 0.8`, `maintenance = 0.6`,
`damage_rate = 0.02`, `repair_cost = 1.5`, `move_cost = 0.1`, `capacity = 10`,
`n = 160`, поле `uniform` (`(2.4+1.6)/2 = 2.0`).

`M·r = 1.6`, `need = 0.6`.

|---|---|---|---|---|---|
| 0.60 | — | 0 (income < need) | 0 | 0 | — |
| 0.70 | 1.429 | 2 | 80 | 79 | — |
| 0.90 | 1.111 | 2 | 80 | 80 | — |
| 0.95 | 1.053 | 2 | 80 | 80 | — |
| 1.00 | 1.000 | 2 | 80 | **52** | 50 |
| 1.20 | 0.833 | 1 | 40 | **42** | 42 |
| 1.60 | 0.625 | 1 | 40 | 40 | 40 |

`income = 1.00` 预测 80，实测 52 — **не сходится**. Разбор ниже.

## Почему при `income = 1.00` не 80

Прямой замер последнего кадра (`--every 2000`):

```
cell 0: field=1.6000 E=10.00 taken=1.000 dmg=0.000 | E=9.40 taken=0.600 dmg=0.000
cell 3: field=1.6000 E=10.00 taken=1.000 dmg=0.000 | E=9.90 taken=0.720 dmg=0.000
cell 11: field=1.6000 E=10.00 taken=1.000 dmg=0.000 | E=10.00 taken=0.744 dmg=0.000
```

Двенадцать клеток держат по два, остальные 28 — по одному. `52 = 28 + 12*2`.

Первый всегда берёт `1.000`, второй — `0.600` … `0.750`. Сумма `1.600` — это
ровно `M·r`, то есть клетка выедена до равновесия. Второй получает **остаток**,
и остаток бывает `0.600` (ровно на грани), а бывает `0.750` — потому что
первый не всегда успевает взять свои `1.0` раньше второго: порядок обхода
меняется, когда организмы двигаются.

`0.600 ≥ need = 0.6` — второй выживает **впритык**. Отсюда и медленное сползание
52 → 50: часть вторых оказывается чуть ниже грани и умирает.

`kSat = 2` верно; неверно было ожидание, что все 40 клеток заполнятся до двух.
Клетка отдаёт `M·r` в шаге, а суммарный спрос двух — `2·income = 2.0 > 1.6`,
поэтому второй живёт только пока первый не забрал всё.

## Почему при `income = 1.20` не 40, а 42

```
cell 3: field=1.6000 E=10.00 taken=1.200 dmg=0.000 | E=9.87 taken=0.496 dmg=0.000
cell 6: field=1.6000 E=10.00 taken=1.200 dmg=0.000 | E=9.08 taken=0.500 dmg=0.000
```

`0.496 < need = 0.6`. Второй **не может** жить на этой клетке постоянно: каждый
шаг он теряет `0.6 − 0.496 = 0.104`. Но его энергия `9.87`, а не 10.00 — он не
сидит на месте. Он ходит между клетками: на одной берёт `1.2` (сыт), на другой
`0.5` (голоден). Средний доход держит его живым.

Значит `kSat` — это **статическая** ёмкость. Динамическая может быть чуть
больше, потому что организм с запасом энергии переживает голодные шаги.
`42 = 40 + 2` — ровно два таких ходока.

## Итоговая формула

```
need  = maintenance                       (если энергии хватает чинить урон до 0)
kSat  = 0                                 если income < need
      = ⌊(M·r − need) / income⌋ + 1        иначе
alive ≈ cells · kSat                      статически
alive ≥ cells · kSat                      динамически (запас энергии разрешает больше)
```

## Что это не доказывает

1. **Не доказывает**, что `need = maintenance` всегда. Если `damage_rate` велик
   настолько, что `maintenance + damage_rate*repair_cost > M·r`, организм не
   может ни жить, ни чиниться, и `need` становится больше. Проверен один режим.
2. **Не доказывает**, что 52 — равновесие. 2000 → 20000 дало 52 → 50, то есть
   ещё падает. Долгий предел не измерен.
3. **Не доказывает**, что 42 стабильно: 2000 и 20000 оба дали 42, но это два
   замера, а не предел.
4. **Не доказывает**, что `kSat` — верхняя граница динамически. Наоборот,
   `income = 1.20` её превышает.
5. **Не доказывает** ничего про `feed = true` (сначала рост, потом еда) — там
   порядок другой.

## Защита

**Стоимость шага ≠ стоимость поддержания.** `maintenance + damage_rate*repair_cost`
выглядит как «сколько стоит шаг», и это правда — но только для организма,
которому есть что чинить. Сытый организм чинить не платит. Ошибка была в том,
что величину, посчитанную для худшего случая, подставили в формулу ёмкости,
где нужен установившийся режим.

Проверка, которая бы это поймала: спросить, **какое `damage` стоит в
установившемся режиме**, до того как считать `need`. Ответ `0` виден в trace
(`dmg=0.000` у всех сытых) и был доступен с самого начала.
