## 2. Вопросы

Каждый вопрос: **контекст → варианты → что мы думаем → что изменит наше мнение → цена → критерий готовности**.

### В1. Где живёт структурированная запись литературы?

**Контекст.** 88 записей `L-NNN` в [`docs/ELEPHANT-LITERATURE.md`](ELEPHANT-LITERATURE.md) — человеческий
markdown: «Кто / Ссылка / Проверено / Утверждение». Машина читает его регулярками в
[`kg/migrate.py:129`](../kg/migrate.py) и только что научилась проверять наличие файла. Для контракта нужны
поля: локатор, артефакт, sha256, дата, `via`, исследованные диапазоны.

**Варианты.**
- **(а) JSON-блок внутри каждой `### L-NNN` секции.** Один источник истины, markdown парсится тривиально,
  человек продолжает читать реестр как реестр.
- **(б) Sidecar `kg/literature-access.jsonl`.** Markdown — журнал для человека, машина читает sidecar;
  дублирования нет, но появляются две правды, которые надо синхронизировать.

**Что мы думаем:** (а), пока записей меньше 150. В (б) главный риск — расхождение md и sidecar
(«кто главный?»), а выгода (простота парсинга) невелика: 88 блоков парсятся один раз.

**Что изменит мнение:** если блоки станут длиннее ~15 строк или если markdown-таблицы понадобятся для
чтения человеком — тогда sidecar, а md генерируется.

**Цена:** 0,75 круга (схема + парсер + миграция 88 записей).
**Готовность:** подсунутая запись `full_text_examined` без файла и sha даёт FAIL; обратный индекс ловит
файл в `papers/` без записи `≥ fragment_read`.

### В2. Порядок ближайших кругов: целостность или инструмент?

**Контекст.** Два внешних разбора разошлись. №1: P0 → контракт+схема → инструмент (A+H+K) → проверки.
№2: сначала целостность (F+B+C+I), потом инструмент, потому что «A без B ускоряет наполнение реестра,
который не умеет себя проверять».

**Варианты.**
- **(а) целостность:** контракт литературы (B) → аудит DOI (C) → журнал литературного круга (I) →
  разделение `checks/` (F) → потом `litsearch` (A).
- **(б) инструмент:** `litsearch`+RRF+снимки (A) → бюджет (H) → skill (K) → потом контракт.

**Что мы думаем:** (а). P0 показал, что дыра не гипотетическая: две записи получали «сильное»
свидетельство, не имея текста. Инструмент без контракта ускорит именно это.

**Что изменит мнение:** если владельцу нужны новые находки в ближайшие две недели (наука важнее
инфраструктуры) — тогда (б), но с условием: снимки пишутся в `literature/runs/` сразу в схеме §3.

**Цена:** (а) ≈ 3,75 круга; (б) ≈ 2,5 круга.
**Готовность:** пакет целиком — гейт зелёный, `log_check` без расхождений, один литературный круг проведён
по новым правилам.

### В3. Модель эмбеддингов: мультиязычная или английская?

**Контекст.** [`tools/semantic_search.py`](../tools/semantic_search.py) использует `bge-small-en-v1.5`.
Наши тексты (заметки, определения, находки) — **русские**, пул документов — **английские** абстракты.
Проверено: на концептуальный запрос нужная статья попадает на 3-е место; при полисемичном seed `repair`
она выпадает совсем (`SCIENCE-STACK.md` §6).

**Варианты.**
- **(а) `multilingual-e5-small`** (384 dim, префиксы `query:`/`passage:`) — межъязыковой retrieval сразу.
- **(б) оставить `bge-small-en`** и мерить только после экзамена Q11.
- **(в) `bge-m3`** (1024 dim) — дороже по памяти и времени, брать только по результату экзамена.

**Что мы думаем:** (а) + отдельный экзамен: без него «стало лучше» — самоощущение. Память не проблема:
560×384×4 ≈ 0,9 МБ; узкое место — загрузка модели, не индекс.

**Что изменит мнение:** экзамен покажет, что разрыв между (а) и «переведённый запрос + б» меньше 1 позиции
MRR — тогда (б) достаточно.

**Цена:** 0,5 круга на переключение, 1 круг на экзамен.
**Готовность:** три конфигурации на одном замороженном пуле: e5-ru, bge-перевод, bge-ru; отчёт с CI.

### В4. Кандидаты литературы: файл, каталог или новая схема узла?

**Контекст.** Поля `lifecycle` в узлах нет (§1.2). Предложение «карантин вне графа» требует решить, где
живут кандидаты и чем они отгорожены. Ещё есть вопрос квоты: 5–10 кандидатов за круг — это бюджет обзора
или научный инвариант?

**Варианты.**
- **(а) `kg/candidates.jsonl`** — один файл-карантин, TTL-архив раз в месяц, дедуп по DOI против графа.
- **(б) `literature/inbox/<run>.json`** — кандидаты по прогонам, ближе к сырью поиска.
- **(в) ввести `lifecycle` в схему узла** и держать кандидатов в `nodes.jsonl` с фильтром в `map/find`.

**Что мы думаем:** (в) — худший: фильтрация сейчас отсутствует (`hidden()` не вызывается в `map/find`),
значит кандидаты мгновенно попадут в навигацию. (а)+(б): сырьё — в `literature/`, кандидаты в граф —
одним файлом. Квота — на `admit`, не на ingest.

**Что изменит мнение:** появление второго оператора (нужна конкурентная запись) или 500+ кандидатов.

**Цена:** 1 круг (+0,5, если вводить `lifecycle`).
**Готовность:** ingest 50 кандидатов не меняет `wc -l kg/nodes.jsonl` и вывод `kg.py map`; `admit` без ребра
к существующему узлу отказывает.

### В5. Снимки поиска: где и в каком виде?

**Контекст.** `results/` восстанавливается `git checkout -- results/` — значит поисковые снимки там
потеряются. Схема снимка должна позволять **replay офлайн** (пересчитать дедуп и RRF из сохранённых рангов),
а `refresh` — это отдельное действие.

**Варианты.**
- **(а) `literature/runs/<run>.json`** + `literature/schema/litsearch-v1.schema.json`, проверка
  `checks/litsearch_contract.py` пересчитывает дедуп и RRF.
- **(б) `results/litsearch/`** — привычно, но противоречит восстановлению `results/`.
- **(в) `papers/` рядом с текстами** — смешивает артефакты разного назначения.

**Что мы думаем:** (а). Схема — §3.

**Что изменит мнение:** если снимков станет так много, что git начнёт тормозить (>1000 файлов) — тогда
архив в `literature/runs/YYYY-MM/`.

**Цена:** 0,5 круга на каркас.
**Готовность:** `--offline --from-run <id>` даёт побайтово тот же рейтинг; ручная правка `rrf` без правки
рангов — FAIL.

### В6. Артефакт для `abstract_read`: обязателен или нет?

**Контекст.** Абстракты часто приходят из API без лицензии на локальное хранение (Crossref, OpenAlex
отдают текст, но не всегда разрешают держать копию). При этом `full_text_examined` без файла — ложь, которую
мы только что запретили.

**Варианты.**
- **(а) необязателен**, но обязательны `via` (канал/endpoint), `retrieved_at` и локатор (DOI/arXiv/PMID).
- **(б) обязателен** сохранённый текст абстракта (маленький JSON/MD в `literature/abstracts/`).
- **(в) отдельный уровень** `abstract_cached` — с файлом, и `abstract_read` — без.

**Что мы думаем:** (а): требование файла для абстракта сделает половину реестра красной без пользы; а вот
`via` и `retrieved_at` — дешёвые и проверяемые.

**Что изменит мнение:** если аудит покажет, что по спорным утверждениям абстракты менялись в API — тогда (б)
для записей, на которые ссылаются claims.

**Цена:** входит в B.
**Готовность:** запись `abstract_read` без `via`/`retrieved_at` — FAIL; с ними — ok.

### В7. Правило PROTOCOL: закрыть дыры для `.sh` и `.js`?

**Контекст.** [`checks/protocol_checks.py:40`](../checks/protocol_checks.py) ищет только `checks/…py`.
`run.sh` вызывает и `.sh` (`stub_links.sh`, `cli_refuses_bad_numbers.sh`), и `audit.js` через node.

**Варианты.** (а) расширить регулярку до `\.(py|sh|js)`; (б) оставить, но записать исключение в PROTOCOL.
**Что мы думаем:** (а) — дыра существует ровно в том месте, где проверяют честность гейта.
**Цена:** 0,25 круга. **Готовность:** удаление строки из PROTOCOL для `.sh`-проверки даёт FAIL.

### В8. `results/` и сетевые артефакты: нужна ли проверка?

**Контекст.** `results/` — 128 каталогов, 592 файла; проверяется только схема `run-*.json`
([`checks/contract.py`](../checks/contract.py)). Литературные снимки туда класть нельзя (В5), но и запрет
никак не проверяется.

**Варианты.** (а) правило «в `results/` только прогоны модели» + проверка «нет `literature/`-подобных
файлов»; (б) ничего не проверять, полагаться на дисциплину.
**Что мы думаем:** (а) — дешёвая проверка, закрывает будущую путаницу.
**Цена:** 0,25 круга. **Готовность:** подсунутый `results/litsearch/x.json` — FAIL.

## 3. Схема, которую предлагаем принять (для критики)

### 3.1 Запись L-NNN (внутри markdown, вариант В1-а)

```json
{"L":"L-060",
 "locator":{"doi":"10.1016/j.biosystems.2025.105567","arxiv":"2411.17012","pmid":null},
 "access":{"level":"full_text_examined","artifact":"papers/arXiv-2411.17012-brown-vittadello.txt",
           "sha256":"<64 hex>","bytes":81691,"retrieved_at":"2026-11-21","via":"ar5iv"},
 "inspection":{"scope":"full","reviewed_ranges":[{"type":"section","value":"3.2 ; 3.4"}]},
 "legacy":false}
```

`level ∈ {metadata_only, abstract_read, fragment_read, full_text_examined, secondary_only}`.
Инварианты: `fragment_read|full_text_examined` ⇒ артефакт + sha; `scope ≠ full` ⇒ непустые `reviewed_ranges`;
файл в `papers/` без записи `≥ fragment_read` — FAIL.

### 3.2 Снимок прогона (`literature/runs/`)

Группы полей: `schema`, `run_id`, `created_at`; `environment` (commit, версии инструментов и модели);
`query` (текст, язык, seeds); `channels[]` (имя, источники, `status: ok|empty|error|skipped_budget`,
`elapsed_ms`, `cost_usd_est`, параметры, `raw_snapshot`, `results[]{rank, ids, title, year, score_kind}`);
`dedup` (метод, кластеры); `fusion` (`rrf`, k, веса, ranking с рангами по каналам);
`degraded`; `saturation` (предыдущий run, прирост, Jaccard топ-20).

Критерий поля: нужно (а) для replay без сети, (б) для ingest как evidence, (в) для сверки позже.
Всё остальное — не включать.
