**Дата:** 2026-11-20. **Посылка:** решения по `T-01…T-12` приняты ([`KG-BRIEF-3-VERDICTS-2026-11-20.md`](KG-BRIEF-3-VERDICTS-2026-11-20.md)),

## A. То, что решает только владелец

### U-01 · Десять определений: утвердить одной строкой
**Контекст.** T-01: определения пишутся **до** разметки. Проверено разборами: без 10/10 разметка не валидируется
(I-02). Пограничные пары, где границы поплывут первыми: **Выбор ↔ Агентность**, **Граница ↔ Порог**, **Индивидуальность ↔
Свои условия**.
**Что нужно.** Либо «подтверждаю, `lines_version: 1`» — и я пишу десять `definition`-узлов по структуре «входит /
не входит / 2–3 пограничных случая / правило для пограничной пары»; либо ваши формулировки.
**Цена откладывания.** Круг 1 стоит: разметка 88 записей и все мосты лягут в язык, который потом менять дороже.

### U-02 · Бюджет разметки судьи: 28, 50 или 80
**Контекст.** Наша симуляция: при истинной κ = 0.70 правило 0.7/0.55 пропускает судью в 33 % при n = 30, 39 % при
n = 50, 40 % при n = 80. То есть **увеличение n само по себе почти не помогает** — мешает ширина бутстрепа при малом n.
**Варианты.** (1) n = 28 (dev-28, отдельной разметки нет) + пограничная зона; (2) расширить dev до 80–100 вопросов;
(3) калибровать на 50 отложенных пунктах, которых нет в экзамене.
**Наш уклон.** (3): калибровка не должна расходовать экзаменационные предметы; иначе T-11 и T-12 конфликтуют.
**Цена.** (3) — около 50 меток владельца один раз плюс ~10 арбитражей.

### U-03 · Пограничная зона судьи: добор или ужесточение
**Варианты.** (1) `κ̂ ∈ [0.60, 0.75)` → добор 30–50 **новых** пунктов; (2) сразу отказ, без добора; (3) принять как есть
с пометкой «слабый судья».
**Наш уклон.** (1) с запретом реролла: повторный прогон тех же пунктов обнуляет гарантию.

### U-04 · Что считается `exam_ready` для моста
**Контекст.** Лестница принята, но список обязательных полей не зафиксирован как данные.
**Варианты.** (1) все семь полей + `check` зелёный; (2) семь полей, `check` — предупреждение; (3) шесть полей без
`falsification`.
**Наш уклон.** (1). Без фальсификатора мост нельзя опровергнуть, а значит нельзя и проверить.

### U-05 · Политика `lines_version: 2`
**Варианты.** (1) новая версия только при смене **границ** определения; (2) при любом уточнении формулировки; (3) только
вручную.
**Наш уклон.** (1): иначе переразметка становится вкусовой и корпус будет дрейфовать без причины.

## B. Механика, которая требует выбора, а не знания

### U-06 · Событие допуска: где хранится
**Контекст.** T-09/T-10: каждое изменение статуса — событие; `admit` требует rationale и evidence.
**Варианты.** (1) `kg/admissions.jsonl` (append-only, вне узлов); (2) поле `events: []` в узле; (3) git-коммит как событие.
**Наш уклон.** (1): узлы остаются читаемыми, история — отдельным потоком, и её можно проверять кодом.

### U-07 · T-13: инвалидация зависимостей — насколько глубоко
**Варианты.** (1) один шаг (правка claim → его мосты и supports в `at_risk`); (2) транзитивно по цепочке; (3) только по
прямым ссылкам в `evidence`.
**Наш уклон.** (1): транзитивное понижение на 534 узлах без нужды создаст волну ложных `at_risk`.

### U-08 · T-14: tombstone — что видно снаружи
**Варианты.** (1) узел остаётся с `status: tombstone`, скрыт из `atlas`/`expand`, виден `show --all`; (2) скрыт везде;
(3) удаляется физически с записью в `ELIMINATED`.
**Наш уклон.** (1): «история не переписывается» — это и про удаление тоже.

### U-09 · Holdout: где физически
**Варианты.** (1) офлайн-файл у владельца, выдача по одному вопросу; (2) отдельная машина; (3) отдельный репозиторий с
правом доступа только у владельца.
**Наш уклон.** (1) сейчас, (2) при автоматизации. Важно: агент не должен получать подробные разборы провалов holdout —
только агрегат.

### U-10 · Что считать вехой для holdout
**Варианты.** (1) каждые 10 кругов; (2) смена `graph_hash` на «крупную» (мосты/схема); (3) по вашему решению.
**Наш уклон.** (2): holdout расходуется по событию, а не по календарю.
