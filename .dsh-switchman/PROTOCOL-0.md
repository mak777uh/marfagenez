# PROTOCOL-0 — четыре пункта с автоматическим вердиктом

**Зачем.** Пятый круг показал: пункты плана, у которых нет носителя вопроса,
проходят как «результат». Этот протокол вводит **гейт пригодности** до
измерения: каждый пункт сначала отвечает «можно ли вообще спрашивать», и только
потом — «что ответил мир».

**Четыре исхода** (пятый добавлен к `AGENTS.md` §4):

| исход | когда |
|---|---|
| `passed` | гипотеза подтвердилась, контроли прошли, носитель был |
| `failed` | гипотеза не подтвердилась, контроли прошли, носитель был |
| `void` | контроль провален — измерение недействительно |
| `insensitive by construction` | арифметика §1 говорит, что плечи не различаются |
| **`not applicable`** | **носителя вопроса нет: измерение не определено** |

**Разница между `void` и `not applicable`.** `void` — мы спросили, но
инструмент сломался. `not applicable` — мы не могли спросить: событие
недостижимо, окно не стационарно, предикат не зависит от состояния.

## Пункт 0. Объявить класс альтернатив

**До любого измерения.** Segura 2026: консервативность панели определена только
относительно класса моделей. Класс не объявлен ⇒ вопрос о достаточности панели
не определён.

**Класс (v1):**

| # | модель | что различает |
|---|---|---|
| A | внутреннее производство границы | граница производится системой |
| B | внешняя поставка границы | граница приходит извне |
| C | односторонний автокатализ без поддержания границы | есть рост, нет поддержания |
| D | граница без производимого ремонтного аппарата | есть граница, нет ремонта второго порядка |

**Вердикт пункта 0:** `passed`, если класс объявлен и записан в файл. Иначе —
`not applicable` для всех последующих пунктов.

**Статус: объявлен (этот файл).**

## Пункт 1. Инвентаризация трасс

**Вопрос:** сколько у нас **независимых** временных серий?

**Команда:**

```bash
cd /root/marfagenez
find results -name 'trace-*.json' -print0 | sort -z | xargs -0 sha256sum > /tmp/traces.sha
awk '{print $1}' /tmp/traces.sha | sort | uniq -c | sort -rn | head
```

**Классы:**

| класс | признак |
|---|---|
| `independent` | уникальный хэш, уникальный `seed`, длина ≥ 100 шагов |
| `duplicate` | совпадающий хэш с другой трассой |
| `final-frame-only` | одна запись состояния, шаг = 3000 |
| `too-short` | длина < 100 шагов |
| `not-applicable` | не содержит временного ряда |

**Вердикт:**

- `passed` — есть ≥ 20 `independent` серий длиной ≥ 300 шагов;
- `failed` — `independent` серий < 20;
- `not applicable` — `independent` = 0.

**Предсказание:** `failed` или `not applicable` — публично видно 6
многошаговых трасс.

**Что даёт:** если `failed`, пункт 2 не запускается, и мы сразу переходим к
пункту 4 (генерация новых трасс внутри окна).

### Результат прогона (2026-11-15)

Скрипт: `.dsh-switchman/inventory.py`. Всего **131** файл `trace-*.json`.

| класс | сколько |
|---|---|
| `independent` | **4** |
| `duplicate` | 19 |
| `too-short` | 6 |
| `final-frame-only` | 102 |
| `unreadable` | 0 |

Независимые: `sighted/trace-sighted-1794435228.json` (200 кадров),
`random/`, `remember/`, `stay/` — по 100 кадров, все `seed = 20250101`.
Серий длиной ≥ 300 шагов — **0**.

**Вердикт п.1: `failed`.** Порог ≥ 20 независимых серий по ≥ 300 шагов не
выполнен: есть 4 серии по ≤ 200 кадров.

**Дубликаты не случайны.** `protocol-capacity/trace-proportional-n60-M2.0-r{0.8,
0.825,0.85,0.875}-t0.6-m{0.5,0.55}.json` — один хэш `a3fd6906f0f7b955…` на
четыре файла с **разными параметрами**. Параметр `r` не дошёл до симуляции.
Это ровно тот случай, который `AGENTS.md` §3 объявляет `void`: «совпадение
хэшей значит, что плечи не различились: либо параметр не дошёл до симуляции,
либо плечи одинаковы по построению».

**Следствие:** пункт 2 на этих данных не запускается. KLD остаётся
`not applicable`, и это записывается как `not applicable`, а не как «драйв
декоративен».

## Пункт 2. Гейт стационарности

**Вопрос:** есть ли окно, где процесс можно считать стационарным?

**Команда:** (после пункта 1, только на `independent` сериях)

```
для каждой серии:
    разбить на окна длины L ∈ {50, 100, 200, 500}
    в каждом окне: mean и std для energy, damage, field_total
    окно стационарно, если |mean(первая половина) − mean(вторая)| < 2·std/√(L/2)
```

**Вердикт:**

- `passed` — есть ≥ 3 серии с ≥ 1 стационарным окном;
- `failed` — стационарных окон нет;
- `not applicable` — серии короче минимального окна.

**Ловушка, которую надо обойти:** состояние «на потолке энергии, `damage ≡ 0`»
формально стационарно, но по существу поглощающее — выйти можно только умерев.
**Такие окна помечать `absorbing` и не считать стационарными.**

### Результат прогона (2026-11-15)

Скрипт: `.dsh-switchman/stationarity.py`, запущен на 6 сериях ≥ 100 кадров
(4 независимые + 2 дубликата, дубликаты не исключались — это отдельная
проблема п.1).

| серия | одинаковых полей подряд | L=50 стационарных | L=100 |
|---|---|---|---|
| `sighted-1794435228` | **184 / 199** | 4 / 4 | 2 / 2 |
| `remember-1794419397` | **99 / 99** | 2 / 2 | 1 / 1 |
| `stay-1794419397` | **99 / 99** | 2 / 2 | 1 / 1 |
| `sighted-1794434500` | 0 / 199 | 4 / 4 | 2 / 2 |
| `sighted-1794434501` | 0 / 199 | 3 / 4 | 1 / 2 |
| `random-1794419397` | 0 / 99 | **0 / 2** | **0 / 1** |

**Вердикт п.2: `passed` формально, `absorbing` по существу.**

Три серии из шести — это **буквально неподвижное поле**: `remember`, `stay`
и `sighted-1794435228` не меняют поле вообще (184 из 199 кадров идентичны
предыдущему). Окна в них «стационарны» потому, что в них ничего не
происходит. По ловушке самого протокола их надо помечать `absorbing` и **не
считать стационарными**.

Остаются три серии, где поле реально меняется: `sighted-1794434500`,
`sighted-1794434501`, `random`. Из них `random` **не стационарен ни в одном
окне** — это единственный режим, где есть настоящая динамика, и он не
стационарен. Две `sighted` формально стационарны при L=50.

**Что это значит для KLD.** Считать KLD не на чем: либо поле не меняется
(сравнивать нечего), либо не стационарно (KLD между разными режимами не
означает «драйва»). **KLD остаётся `not applicable`**, и причина названа:
нет ни одной серии, где поле одновременно меняется и стационарно.

**Что это не доказывает.** Отсутствие стационарности у `random` может быть
артефактом длины (100 кадров с шагом 20). На 5000 шагах картина может быть
другой. Это не проверено.

## Пункт 3. Причины смерти — скан по двум осям

**Вопрос:** при каких параметрах смерть от урона достижима?

**Команда:**

```
для taken ∈ {0.000, 0.05, …, 1.000}:
  для damage_rate ∈ {0.001, 0.01, 0.1}:
    World::default() с этими двумя полями, один организм, 5000 шагов
    записать: причина смерти ∈ {energy, damage, both, alive}
```

**Вердикт:**

- `passed` — есть параметры, где доля траекторий с причиной `damage` > 5 %;
- `failed` — ни при каких параметрах из сетки полоса не шире 5 %;
- `not applicable` — сетка не покрывает ни одного режима со смертью.

**Поправка к пятому кругу:** скан по одной оси `taken` при умолчаниях даёт
пустую полосу, но при `damage_rate = 0.1` коридор входа в срыв починки —
`energy ≤ 0.15` вместо `0.015`, а шагов до смерти от урона — 10 вместо 100.
**Ось `damage_rate` обязательна, иначе вывод «носителя нет» относится к одной
точке параметров.**

### Результат прогона (2026-11-15)

Скрипт: `.dsh-switchman/death_scan3.py` — точная копия шага из
`core/src/organism.rs:420-460`, сетка `income × damage_rate` = 8 × 6 = 48 точек,
5000 шагов, старт с полной клетки (`energy = capacity = 10`).

**Вердикт п.3: `passed`.** Смерть от урона достижима в 16 точках из 48.

| income | dr | шаг смерти от урона |
|---|---|---|
| 0.5 | 0.5 | 12 |
| 0.6 | 0.01 / 0.05 / 0.1 / 0.2 / 0.5 | 765 / 152 / 76 / 37 / 14 |
| 0.65 | 0.05 / 0.1 / 0.2 / 0.5 | 419 / 110 / 44 / 15 |
| 0.7 | 0.1 / 0.2 / 0.5 | 209 / 54 / 16 |
| 0.8 | 0.2 / 0.5 | 104 / 19 |
| 1.0 | 0.5 | 29 |

Распределение по всей сетке: урон 16, голод 17, жив 15.

**Механизм, который пятый круг не видел.** Ремонт в core — «всё или ничего» по
цене `damage * repair_cost` (`organism.rs:441-448`), а `damage` растёт на
`damage_rate` за шаг (`organism.rs:431`). Если ремонт не прошёл, на следующем
шаге цена уже `2·dr·repair_cost`, потом `3·dr·repair_cost` — **цена растёт
линейно с накопленным уроном, а энергия падает**. Срыв починки самоусиливается.
Моя первая модель (`death_scan.py`) считала цену как `dr * repair_cost`, то есть
постоянной, — и потому не воспроизвела смерть от урона. **Ошибка была в модели,
не в core.**

**Следствие для вопроса о носителе.** Утверждение «смерть от урона при
умолчаниях недостижима» верно только для `income = 1.0`, `dr = 0.01`, старта с
полной клетки. При `income = 0.6` и `dr = 0.01` организм умирает от урона на
шаге 765, а энергия в момент смерти — `0.01`. То есть он не голодает: он
балансирует на пороге починки и срывается. Это **не** «носителя нет» — это
носитель, который включается в узкой полосе `income ≈ maintenance_cost`.

**Что это не доказывает.** Скан — один организм на пустой сцене, без поля и без
политик. Он говорит, что урон *может* убить при таких параметрах в изоляции.
Он не говорит, что в реальной симуляции с полем и движением полоса шире или
уже. Проверка на трассах — отдельный пункт.

## Пункт 4. `shared-core` — три обязательных теста

**Вопрос:** существует ли минимальное общее причинное ядро?

**Условия** (по пятому кругу §1.8 + наше дополнение):

1. `H ≠ ∅`;
2. `H` сам — свидетель и COT, и RAF;
3. в `H` есть ненулевой допустимый продуктивный поток;
4. включительная минимальность: никакая собственная подсеть `H` не
   удовлетворяет обоим.

**Тесты самого алгоритма** (обязательны до применения к содержательной сети):

| тест | сеть | ожидание |
|---|---|---|
| разделённые свидетели | `X(COT) ∪ Y(RAF)` без связи | `false` |
| тривиальное ядро | сеть, где `H = G` проходит | `false` |
| положительный | сеть с известным ядром | `true`, ядро совпадает |

**Вердикт:**

- `passed` — все три теста алгоритма прошли **и** содержательная сеть дала ядро;
- `failed` — алгоритм прошёл тесты, содержательная сеть ядра не дала;
- `void` — тесты алгоритма провалены;
- `not applicable` — содержательной сети нет.

**Важно:** результат на **игрушечной** сети — это юнит-тест, не находка.
В `POSITIVE.md` он не попадает.

### Результат прогона (2026-11-15)

Скрипт: `.dsh-switchman/shared_core4.py`. Четыре версии, три провала — и это
главный результат пункта.

| версия | счёт | что провалилось | чей дефект |
|---|---|---|---|
| v1 | 1/3 | обе отрицательные сети прошли как «ядро» | **постановки** |
| v2 | 2/3 | положительный контроль отвергнут | **реализации** |
| v3 | — | отладка: `is_cot` и `is_raf` дают `True`, цикл — `False` | — |
| v4 | **3/3** | — | — |

**v1 — дефект постановки.** У COT-замкнутости и RAF нет требования
нетривиальности. Одиночная реакция `A -> B` без катализатора COT-замкнута и
формально RAF (нет катализатора — нечего проверять). Поэтому «ядро» из одной
реакции находилось в сети, где по замыслу ядра нет. Это ровно то, о чём
предупреждает RESEARCH-BRIEF-6 §1.4 вопрос 1: **hitting set не обязан быть
подсетью, свидетельствующей оба свойства.** Добавлено `|H| ≥ 2` и требование
каталитического цикла.

**v2 — дефект реализации.** `has_catalytic_cycle` исключал `i == j`, а в
положительном контроле `{A -> B cat B, B -> A cat A}` обе реакции
самокаталитичны. Самокатализ — это петля длины 1, её нельзя выкидывать.

**v4 — `passed` 3/3.** Алгоритм различает сети: отвергает разделённых
свидетелей, отвергает тривиальное ядро, находит положительный контроль.

**Общий вердикт пункта 4: `not applicable`.** Алгоритм готов, но
**содержательной сети у нас нет** — по таблице протокола это именно
`not applicable`, а не `failed`. Мы не спрашивали мир о нашем организме; мы
спрашивали только о своём инструменте.

**Что это не доказывает.** Три теста на сетях из 1–4 реакций не доказывают,
что алгоритм масштабируется до 10–50 реакций и что перебор подмножеств там
выполним (2⁵⁰ — нет). Вопрос о hitting set vs пересечение irrRAF из
RESEARCH-BRIEF-6 §1.4 остаётся **открытым**: наша реализация ищет
минимальное по включению подмножество перебором, а не hitting set, и на
больших сетях это не тот объект.

## Пункт 5. Тест неразличимости (поправленный)

**Вопрос:** различает ли панель внутреннее производство границы от внешней
поставки?

**Поправка к пятому кругу.** Не подбирать совпадение — искать его.

```
класс B(v): внешняя поставка ∅ → M со скоростью v ∈ [0, 10]
для каждого v: прогнать B(v), измерить d(v) до A по (energy, damage, M, t_death)
d* = min_v d(v)
ε = шум между репликами A с разными сидами
```

**Вердикт:**

- `passed` (панель различает) — `d* ≥ ε` для всех `v`;
- `failed` (панель не различает) — `d* < ε` хотя бы для одного `v`;
- `not applicable` — модель A не построена.

**Почему это не результат по построению:** мы не выбираем `v`, чтобы совпало;
мы ищем минимум и сообщаем его. Тест может провалиться в обе стороны.

## Порядок и зависимости

```
0 (класс) ──┬── 1 (инвентаризация) ── 2 (стационарность) ── KLD (отложен)
            ├── 3 (причины смерти)
            └── 4 (shared-core)
5 (неразличимость) — после 1.1A (граница как переменная), иначе модели A нет
```

**KLD отложен до пункта 2.** Если пункт 2 даёт `failed`/`not applicable` —
KLD не запускается, и это записывается как `not applicable`, а не как
«драйв декоративен».

## Что этот протокол не доказывает

Он не доказывает, что слон нащупан. Он доказывает только, что каждый пункт
**мог** провалиться и не провалился по правильной причине. Достаточность панели
относительно класса альтернатив — отдельный вопрос (Segura 2026), и он решается
пунктом 5, а не этим протоколом.
